## 6. Owner decisions and operations material

### 6.1 D3: legacy archived courses (read-only report + procedure)

- **Earlier query (OWNER_DECISIONS D3):** valid and read-only, but a superset. Its joins are `enrollments → courses`; its filters are course ARCHIVED, enrollment ARCHIVED, `ADMIN_APPROVAL` and `approvedAt IS NOT NULL`. That also matches every genuinely approved student, and courses archived after the fix, where the defect cannot occur.
- **New report:** `sql/d3-candidate-report.sql`, SELECT only. It restricts to open archive records without the recorded-ids key, and classifies each row from the audit log, up to the archive time:
  - a request (`ENROLLMENT_CREATE` with `after.state = PENDING_APPROVAL`) newer than the last approval (`ACCESS_GRANT`) → `RESTORE_AS_PENDING_APPROVAL`;
  - otherwise `APPROVED_RESTORE_AS_ACTIVE`;
  - no audit evidence → `MANUAL_REVIEW`.
  - Output has ids only. Treat it as personal data anyway.
- **Remediation:** `sql/d3-remediation-template.sql`. It writes production data, so it is **run only with explicit authorisation**. It changes no enrollment: it adds the reviewer-confirmed ids to the open archive record, under the key the fixed restore reads. Restoring from the dashboard then returns them to PENDING_APPROVAL. It is idempotent and has a rollback.
- **Tested [test]** on a throwaway PostgreSQL 16 with the real migrations, rolled back. Every seeded case classified correctly, a second remediation run changed nothing, and no enrollment row was touched.

### 6.2 D5: wallet balance on deletion (policy undecided; no balance or ledger change made)

**Behaviour today [code]:**
- Erasure never touches the wallet or the ledger.
- During the 30 days the balance is unusable, because the holder cannot sign in.
- After erasure the wallet drops out of the admin wallet list (`deletedAt: null` filter), and `adjust` refuses the user.
- There is no total of liabilities left on deleted accounts.

| Question (from D5) | Technical / reporting consequence of each answer |
|---|---|
| 1. Is unused prepaid credit refundable under your terms and consumer law? | **Yes:** settle during the 30 days. Refund outside the app, then an audited `adjust` debit with the reason. Nothing to build if done by support. **No:** keep disclosure only; the balance stays on the ledger. |
| 2. Should a positive balance block deletion until settled, or only be disclosed? | **Block:** a small backend change (refuse `POST /auth/account-deletion` when balance > 0, with a new error code) plus app copy. **Disclose:** already implemented. |
| 3. How should erased accounts' balances appear in your books? | **Liability until written off:** needs a read-only report of balances whose user is deleted (one SQL query or an admin endpoint). **Breakage after N months:** an audited write-off entry per wallet, never deleting rows. |
| 4. Does the answer differ for cash-card credit versus admin top-ups? | **Yes:** the policy must use the ledger entry type and source, which the ledger records. **No:** one rule. |

### 6.3 D6: choosing `TRUST_PROXY_HOPS` (procedure; no production setting changed)

1. Deploy the API release containing the diagnostic (requires your authorisation).
2. From a network whose public IPv4 you know (for example `https://api.ipify.org`), call **directly against the Render URL** with a MASTER token:
   - **A:** `GET /api/v1/admin/diagnostics/client-ip?expectedIp=<your IP>`
   - **B:** the same, with the extra header `X-Forwarded-For: 198.51.100.77`
3. Take the hop counts present in **both** A's and B's `hopCountsMatchingExpected`:
   - **Exactly one:** that is the candidate. A plain call alone always matches every count from the right one up to 10, which is why B is required.
   - **Several:** the platform discards client-written entries. Use the smallest, and note that a platform change could alter this.
   - **None:** do not change anything. Check that the address is right (IPv4 vs IPv6, VPN, carrier NAT) and look at `otherAddressHeaders`.
4. Repeat from a second, different network (for example mobile data). The same count is required.
5. **Minimum evidence:** four saved responses (2 networks × A/B), all consistent, with `forwardedForTruncated: false` on the A calls. They contain only your own address; the proxy secret is never echoed [test].
6. Set `TRUST_PROXY_HOPS` on Render, redeploy, and repeat A and B.
   - Both must show `resolvedIp` = your address.
   - If B shows `198.51.100.77`, revert at once: that value lets clients choose their bucket.
